# M1 — доказ атомарності D1

Перевірено 2026-10-31 на локальному workerd/D1; це перший підкрок M1,
не завершена бізнес-схема чи реалізація команд.

Міграція `0001_transaction_assertions.sql` створює службову таблицю
за D-162. Іменовані CHECK перевіряють 1, NOT NULL не допускає обходу
через NULL. SQL-вставка guard завжди створює рядок через VALUES із CASE;
відсутній профіль дає ELSE 0. Успішний guard видаляється в тому самому batch.

13 інтеграційних тестів використовують файл міграції через офіційні
readD1Migrations/applyD1Migrations та зменшені синтетичні таблиці `__guard_*`.
Після відмови перевіряються всі ефекти: revision, подія, доставка,
результат, лічильник і відсутність залишкового guard. Покрито:

- повторне застосування міграції й успішний batch;
- стару revision та відсутній профіль;
- кожен із п’яти CHECK після всіх змін і окремо NOT NULL;
- changes() = 1/0 усередині batch;
- помилку UNIQUE після видалення guard;
- два одночасно запущені batch з одним ключем: один переможець,
  один набір ефектів, результат відповідає саме збереженій події.

Відтворення: `npm run test:worker`. На момент першого підкроку
загальний `CI=true npm run check`
пройшов: типи, **26 Vitest** (6 unit + 20 Worker), build та **21 Playwright**.
Міграції не застосовували до dev/demo-бази. UI й HTTP-маршрути не змінені.
Read-only перевірка 7 локальних SQLite-файлів не знайшла тестових таблиць
чи transaction_assertions. Незалежне BMAD Build рев’ю не знайшло
доказових дефектів; рев’юер перевіряв код/diff, не повторював запуск тестів.

Межа доказу: перевірено механіку rollback і назви CHECK-помилок на
поточному runtime. Це не гарантія стабільності тексту помилок інших версій
і не доказ авторизації/TTL/посилань/місткості майбутніх команд. Для них
потрібні реальні SQL-предикати та окремі тести. Попередній GitHub CI
перевірив M0; цей підкрок M1 поки перевірений лише локально.

Наступним підкроком додано [бізнес-схему й результати](m1-data-model.md),
і [внутрішній протокол](m1-command-protocol.md), де наведено актуальний
повний прогін: класифікація помилок, selection_revision/retry та чотири
бюджети з capacity_epoch реалізовані для підключення доменних команд.
Пауза після відмови місткості залишається окремою транзакцією за D-163.
Коміт — після завершення цілого M1.
