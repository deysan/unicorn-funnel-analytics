# План роботи

Оновлено: 2026-10-29. Власник рішень: Андрій. Статус: проєктування.

## Принцип роботи

Розбираємо рішення поступово: вимоги й припущення → основні сценарії → модель
даних → архітектура → гарантії та перевірки → implementation plan.
Суттєві результати зберігаємо в Git, не копіюючи повний чат.
Один завершений блок питань — один коміт після повного аудиту; погоджені
рішення та зміни плану до цього накопичуємо в документації.
Погоджено один домен і браузерну ідентичність для MVP (D-003).
Перенесення між браузерами поза MVP. Погоджено поведінку повернення без step
та зі step; VisitID, сесійний таймаут і Amplitude не використовуємо (D-004).
Технічний стек ще не обрано; погоджені припущення та їхні межі — у вимогах.

## Запропонований мінімальний наскрізний зріз

Квіз → збережені відповіді й події → серверний вибір офера → зафіксований перехід
→ тестовий Lead → повторний візит без квізу → Purchase → зміна звіту.
Перевірки включають повтор того самого постбека та другу окрему покупку.

Це початкова пропозиція агента за сценарієм ТЗ, не остаточна декомпозиція робіт.

## Пріоритет найближчого обговорення

UX повторного проходження погоджено (Q-03, D-004–D-007, D-023–D-024).

Бізнес-правила атрибуції та постбеків погоджено (Q-05, D-009–D-012),
вибір за кількох активних Lead — D-008.

Одиниці підрахунку та базові формули конверсій погоджено (Q-02, D-013–D-014).

Конкурентні зміни погоджено: збереження по питаннях, останній успішний
серверний запис перемагає, без синхронізації вкладок наживо (Q-06, D-015).

Географія й latency погоджені: американський регіон, вимірювання зі східного
та західного узбережжя США, p95 основних API ≤ 500 мс для обох точок (D-016).

Гарантія прийняття та політика накопичення погоджені (Q-08, D-017–D-018);
фізичні ліміти й відновлення потребують перевірки під час дизайну.

Базові строки зберігання та активність погоджено (Q-09, D-019, D-025);
узгодження очищення й технічних меж перевіряємо під час дизайну.

Межі доступу погоджено: публічний квіз, закриті звіт і API аналітики,
окрема авторизація постбеків без адмінки (Q-10, D-020).

Кількість прелендів погоджено: один у демо, розділення аналітики перевіряємо
на синтетичних даних двох прелендів (A-02, D-021).

Аудит блоку вимог і рішень завершено; чотири виявлені прогалини опрацьовано.
Висновки й статуси — [аудит вимог](requirements-audit.md).
Фільтр офера погоджено лише для переходів і партнерських результатів
(AU-01 закрито, D-022). Повернення лише з Lead неактивних оферів за достатніх
вподобань пропускає квіз і повторний email (AU-02 закрито, D-023).
Автоматичну імітацію переходу та правила повторів погоджено (AU-03 закрито,
D-024). Активність для строку профілю й Lead погоджено (AU-04 закрито, D-025).
Наступне обговорення — основні сценарії, починаючи з нового користувача:
показ питання → збереження відповіді → вибір офера → імітація переходу → постбек → звіт.

Документацію оновлюємо в міру погодження. Блок Q-01–Q-10 та A-01–A-03
завершено на рівні вимог. Технічні питання мають явний план перевірки
в аудиті; їх не позначаємо вирішеними до виконання відповідних етапів.

## Аудит та завершення блоку питань

1. Повторно звірити рішення з первісним ТЗ, погодженими уточненнями та межами MVP.
2. Перевірити узгодженість вимог, журналу рішень, плану, README та інструкцій
   агенту; усунути застарілі статуси, суперечності й неоднозначні формулювання.
3. Пройти наскрізні й граничні сценарії: новий/повторний користувач, пропуск
   квізу, зміна відповідей, кілька Lead, неактивний офер, повтори й конфлікти,
   конкурентність, порядок і затримки подій, часові межі та відмови.
4. Перевірити формули звіту на контрольних прикладах, узгодженість retention
   з атрибуцією й дедуплікацією, захист ідентичності та персональних даних.
5. Зафіксувати фактичні висновки аудиту, виправити прогалини; нові бізнес-рішення
   обговорити з власником. Відкладені технічні перевірки позначити явно.
   Цей аудит проєктування не підміняє майбутні тести реалізації.
6. Зберегти локальну резервну копію історії й робочих змін. Об'єднати блок
   комітів від `c740cce` до поточного кінця блоку та накопичену документацію
   в один коміт. База — `62d485d`; початкову документацію `096d2ff` і правило
   меж документації `62d485d` залишити окремо. Межі перевірено за поточною
   історією; повторно перевірити перед виконанням.
7. Перевірити повноту підсумкового diff і оновити віддалену гілку через
   force-with-lease з явним очікуваним SHA, не перезаписуючи сторонні зміни.

Аудит завершено 2026-10-29; висновки й межі перевірки — у `requirements-audit.md`.
Дозвіл власника на наведений порядок об'єднання й пушу отримано 2026-10-29.
Результат Git-операцій перевіряємо за історією та SHA віддаленої гілки.

## Початок імплементації

Налаштування Cloudflare виконуємо на початку імплементації, після вибору архітектури.
Погоджена послідовність підготовки: доступ до акаунта → локальний інструментарій
і вхід → мінімальне розгортання для перевірки сумісності → потрібні ресурси,
секрети та логи. Кроки пояснюємо власнику та фіксуємо відтворювані команди в README.
Під час поточного аналізу вимог ресурси Cloudflare не створюємо.
