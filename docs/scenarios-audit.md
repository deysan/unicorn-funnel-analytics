# Аудит сценаріїв перед архітектурним дизайном

Дата: 2026-10-29. Предмет — документація та очікувана поведінка;
код, тести, розгортання і готовність до імплементації не перевіряються.
**Підсумок:** пакет сценаріїв перевірено, виправлення внесено; можна починати
архітектурний дизайн. Невирішених бізнес-суперечностей, що блокують цей
перехід, огляд не виявив. Технічний залишок AR-01–AR-10 не закрито.
Підсумок незалежних рев'ю та їх межі — у
[BMAD-звіті](bmad/reviews/2026-10-29-scenarios/report.md).

## Джерела та спосіб перевірки

Повторно отримано первісне ТЗ через Google Drive; зіставлено з
[вимогами](requirements.md), [рішеннями](decisions.md),
[сценаріями](scenarios.md), [планом](plan.md) і попереднім аудитом.
Матеріали співбесіди та приватне листування повторно не читалися.
Процесне уточнення S2 враховано за раніше зафіксованим статусом.

Незалежні контексти BMAD Review отримали однаковий зафіксований вхід
із SC-01–SC-13 та первісним ТЗ; його хеш і склад збережено в manifest.
Додані після цього контрольні приклади описано нижче окремо: початкові
висновки рев'юерів не є доказом перевірки пізніших змін.

## Виправлення за результатами ручної звірки

- **SA-01 — рівний EPU:** FR-06 містив правило, але SC-01–SC-13 не мали
  окремого контрольного входу. Додано незалежну тестову конфігурацію в SC-05;
  початковий каталог не змінено.
- **SA-02 — числові фільтри й відвали:** D-021–D-022 були погоджені,
  але бракувало спільного контрольного набору з двома прелендами,
  незавершеним квізом і тим самим UserID у кількох зрізах. Додано SC-14.
  Друга сторінка квізу не додається; це синтетичні дані майбутнього тесту.
- **SA-03 — активність у SC-04:** зауваження adversarial прийнято;
  замість «профіль не змінюється» уточнено незмінність відповідей і C3
  при поновленні активності за D-025. Це виправлення формулювання.
- **SA-04 — навігація і статуси:** оновлено BMAD README, каталог сценаріїв
  винесено у вступ, поточний план скорочено. Повна хронологія й уже виконане
  об'єднання Git-історії збережені в `plan-history.md`.

Рубрика `bmad-prd` для початкового знімка: 5 вимірів strong, 2 adequate,
без critical/high/medium, 3 low (SA-01, SA-02 та застарілий BMAD README).
Її висновки перетинаються з ручною звіркою та adversarial; це не окремі
нові дефекти. Усі три виправлено. Структурні рекомендації виконано зі
збереженням історії замість її видалення. SC-04/SC-05/SC-14 після змін
додатково перевірив незалежний контекст — без зауважень.

## Реєстр технічних питань для архітектури

Це явний залишок проєктування, не погоджені механізми й не дозвіл почати код.
Відповідальний за пропозиції — агент архітектури; власник погоджує зміни
бізнес-поведінки. Кожен пункт має бути закритий до реалізації залежної частини.

| ID | Питання | Критерій закриття |
|---|---|---|
| AR-01 | Генерація початку/показів, reload, ререндер, step, час дії проти доставки | Контракт подій із прикладами повторів; повторна оцінка фактичної кількості подій |
| AR-02 | Звіт: часовий пояс, межі періоду, updated_at, повнота історії | Однозначні формули/запити та контроль SC-14; прийнята подія з допуском часу не губиться |
| AR-03 | Записи, ідемпотентність та часткове завершення | Ключі/строки/результати повтору; атомарність відповіді з подією, постбека і ClickID; відновлення SC-09 |
| AR-04 | Узгоджений вибір при зміні відповідей/Lead/активності офера | Момент фіксації рішення, конкурентні випадки; reload старого результату та новий перехід розділені |
| AR-05 | Retention і дедуплікація | Логічне завершення проти фізичного утримання, очищення залежностей/копій, повтор після видалення ClickID, повнота звіту |
| AR-06 | Бюджет і надійна доставка | Події та байти, резервування, поріг відновлення, швидкість розбору, облік втраченого ACK приймача |
| AR-07 | Браузерний доступ і закриті API | Механізми захисту ідентичності, постбеків, звіту, валідації; перевірки SC-13 |
| AR-08 | Продуктивність і вартість | Офіційні гарантії/ліміти/ціни з датою; обсяг усієї історії, p95 обох точок, профіль навантаження |
| AR-09 | Поведінка UI при збої подій показу/no-offer | Визначена поведінка при переповненні для показів, повторна спроба вибору, збереження операції через reload |
| AR-10 | Межі MVP і подальші розширення | Явне розділення коду/імітації/дизайну; майбутні EPU та виключення після Purchase без реалізації зараз |

Реєстр узагальнює [попередній аудит](requirements-audit.md) та відкриті
деталі SC-03–SC-13, а не скасовує їх. Невирішену бізнес-суперечність
не можна закрити простим перенесенням у цей список.
