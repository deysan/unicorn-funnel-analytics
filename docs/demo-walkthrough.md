## Перегляд хмарного звіту без запису подій

Відкрийте [звіт за 1 листопада](https://unicorn-demo.unicorn-deysan.workers.dev/report?from=2026-11-01&to=2026-11-01)
і введіть `demo` / `unicorn-demo` у вікні браузера. Вхід лише для читання;
пароль не додають до URL. [Квіз і перевірка свого результату](../README.md#відтворити-сценарій)
описані на початку README; нижче наведено розширений локальний сценарій.
Перегляньте бізнес-числа, фільтри й технічний стан: `normal`, свіжий Cron,
відсутні паузи й помилки, підтверджена межа історії. Звіт не запускає Cron
і не поновлює профіль. [Поточні спостереження](README.md#перевірка-пакета-2026-11-02).

Нижче — сценарій **локального відтворення**, що записує синтетичні дані.
Під час документаційної перевірки 2026-11-02 його не запускали.

## Підготовка

З кореня репозиторію, Node 24.22.2 / npm 11.19.1:

```sh
nvm use
npm ci
npm run dev
```

Setup створює відсутні секрети/TLS і додавально застосовує міграції 0001–0005;
існуюча `.wrangler/state` зберігається. Не очищайте dev persistence для демо.
Для нового синтетичного UserID почніть **нову приватну сесію**: у Chrome
спочатку закрийте всі попередні приватні вікна, а потім відкрийте нове.
Якщо попередню сесію потрібно зберегти, використайте окремий чистий профіль
браузера. Звичайне додаткове приватне вікно Chrome продовжує чинну сесію
([офіційна довідка](https://support.google.com/chrome/answer/95464?hl=en),
перевірено 2026-11-01) і може успадкувати cookie та Lead попереднього демо.
Залишайте обрану нову сесію відкритою до кінця всіх кроків.
Сторонніх переходів або розсилки немає.

Спочатку відкрийте лише <https://localhost:5173/report/> у цьому приватному
вікні та прийміть локальний self-signed сертифікат. Квіз ще не відкривайте:
саме відкриття його сторінки вже створює вхід і показ питання. Введіть
`REPORT_USERNAME`/`REPORT_PASSWORD` з локального ignored `.dev.vars`
у браузерний Basic Auth діалог. Не виводьте файл у термінал або демонстрацію
екрана; не передавайте credentials у URL, Git, скриншотах чи чаті.
Зафіксуйте базові числа поточного UTC-дня, `preland_id=demo`, без фільтра
офера. Це read-only звіт, він не створює користувача й не поновлює cookie.

Якщо звіт unavailable або технічно недоступний через metadata, зупиніть
числову частину демо й застосуйте [діагностику](report-operations.md).
Дані існуючої dev-бази не стають повними автоматично. Для гарантовано
ізольованого відтворення є браузерний CLI-тест нижче; його окрема тестова
persistence не змінює dev-даних. Не видавайте підготовлений скриншот за
результат неперевіреної dev-історії.

## Квіз → Lead → bypass

Лише після фіксації базових чисел відкрийте <https://localhost:5173/>
у новій вкладці того самого приватного вікна. Оберіть «Жінки» →
«Продовжити» → «Азія» → «Продовжити» →
`Synthetic@example.test` → «Підтвердити та підібрати». Чинний каталог
обирає офер **003**. Екран показує назву, URL і ClickID; зовнішній сайт
не відкривайте. Збережіть **перший** ClickID: обидві Purchase нижче будуть
атрибутовані саме до початкового квіз-переходу.

В іншому терміналі підготуйте тільки необхідний партнерський токен через
env; ці команди його не друкують і не передають в argv/URL. Не вмикайте
shell tracing (`set -x`), не вимикайте TLS-перевірку.

```sh
export PARTNER_TOKEN="$(node --env-file=.dev.vars -p 'JSON.parse(process.env.PARTNER_TOKENS)["demo-partner"]')"
export NODE_EXTRA_CA_CERTS="$PWD/.wrangler/tls/cert.pem"
CLICK_ID='вставте-перший-ClickID-із-квізу'
DEMO_RUN="$(node -p 'crypto.randomUUID()')"
LEAD_FILE="$DEMO_RUN-lead.json"
PURCHASE_FILE="$DEMO_RUN-purchase.json"
SECOND_FILE="$DEMO_RUN-purchase-2.json"

npm run partner -- prepare --file "$LEAD_FILE" --type Lead --click "$CLICK_ID"
npm run partner -- send --file "$LEAD_FILE" --target https://localhost:5173
```

`prepare` друкує `prepared`, `send` — `accepted` після успішної відповіді.
Файл лежить в ignored `.wrangler/partner-events/`; ексклюзивне створення
не дозволяє перезаписати його. Новий `DEMO_RUN` дає нові назви при повторному
демо без очищення даних. Email/відповідей у партнерському файлі немає.

У **тому самому приватному вікні** заново відкрийте корінь
<https://localhost:5173/> через адресний рядок. Не використовуйте reload
готового результату або Back як заміну нового входу. Активний Lead для
003 дає bypass: офер 003 показується без питань/email, ClickID **новий**.
Не замінюйте збережений `CLICK_ID` — він потрібен для перевірки атрибуції
до першого переходу. Кількість унікальних входів і переходів цього
користувача за той самий день не подвоюється.

## Purchase → точний повтор → друга покупка

```sh
npm run partner -- prepare --file "$PURCHASE_FILE" --type Purchase --click "$CLICK_ID" --amount-minor 2500 --currency USD
npm run partner -- send --file "$PURCHASE_FILE" --target https://localhost:5173
npm run partner -- send --file "$PURCHASE_FILE" --target https://localhost:5173
npm run partner -- prepare --file "$SECOND_FILE" --type Purchase --click "$CLICK_ID" --amount-minor 2500 --currency USD
npm run partner -- send --file "$SECOND_FILE" --target https://localhost:5173
unset PARTNER_TOKEN NODE_EXTRA_CA_CERTS
```

Усі send повертають `accepted`. Другий send того самого файла не змінює
даних; інший підготовлений файл має новий PartnerEventID і створює другу
Purchase того самого покупця. Після мережевої помилки повторюйте `send`
того самого файла, а не `prepare`; CLI не слідує redirect. Тільки чинні
429/503 limiter-відповіді мають обмежені автоматичні повтори з Retry-After.
Додатковий конфлікт ID зі зміненим payload показано у [технічній інструкції](development.md#локальна-демонстрація-партнерських-подій).

## Очікувані числа й фільтри

Після кожного кроку натискайте «Оновити» у звіті. Період — UTC-день усіх
кроків, `preland_id=demo`, спочатку всі офери. Уникайте переходу через UTC
північ: інакше Activity розподілиться між днями, а конверсії лишаться
когортними. Поточний день у UI позначено незавершеним.

За нового UserID й відсутності паралельних дій очікуються такі **сукупні
прирости до початкового зрізу** (на порожньому доступному періоді це числа):

| Завершений крок | Входи | Початки / завершення | Переходи | Bypass | Lead | Покупці | Purchase |
|---|---:|---:|---:|---:|---:|---:|---:|
| Квіз і офер | +1 | +1 / +1 | +1 | 0 | 0 | 0 | 0 |
| Lead | +1 | +1 / +1 | +1 | 0 | +1 | 0 | 0 |
| Новий вхід bypass | +1 | +1 / +1 | +1 | +1 | +1 | 0 | 0 |
| Перша Purchase | +1 | +1 / +1 | +1 | +1 | +1 | +1 | +1 |
| Точний повтор | +1 | +1 / +1 | +1 | +1 | +1 | +1 | +1 |
| Друга Purchase | +1 | +1 / +1 | +1 | +1 | +1 | +1 | +2 |

Кожне з трьох питань додає одного унікального користувача до показу та
підтвердження. Для окремого порожнього початкового зрізу питання,
початок→завершення, початок→офер, перехід→Lead/Purchase в кінці мають
1/1 = 100,0%; «ще не підтвердили» — 0/1 = 0,0%. За попередніх даних
перевіряйте пари numerator/denominator, не додавайте відсотки.

- Застосуйте офер `003`: бізнес-прирости вище лишаються; quiz-частина
  повністю незмінна від фільтра офера. Інший офер без подій дає нулі в
  offers і 0/0 «немає даних», залишаючи quiz-частину тією самою.
- `preland_id=demo` відсікає інші преленди; не підсумовуйте їхніх унікальних
  користувачів як загальний результат. Неактивні/historical офери не зникають.
- Зміна форми не змінює звіт до «Застосувати». Перевірте URL і reload;
  невідомий вибраний ID не має мовчки зникати. Дати включні за UTC.
- Старіший за `available_from` період дає `period_unavailable` без чисел.
  `history_unverified` має пріоритет для всіх періодів. Для ручного демо
  недовіри не змінюйте dev D1: цей сценарій покривають ізольовані тести.

## Cron, відмови й межі демонстрації

Доставка та cleanup працюють у scheduled handler; звіт їх не запускає.
Для локального середовища відтворюваний спосіб показати `normal`, `unavailable`,
backoff і відновлення — **ізольовані Worker-тести**, що викликають справжні
handler/executor. Наявність Cron у конфігу не є доказом, що dev-сервер
сам виконав scheduled запуск. Публічного endpoint запуску Cron немає;
цей walkthrough не припускає його існування і не обіцяє оновлення ACK
після простого очікування у браузері.

```sh
npm run test:worker -- tests/worker/delivery.test.ts tests/worker/maintenance.test.ts tests/worker/report-history.test.ts tests/worker/report.test.ts
npm run build
npm run test:smoke -- --project=chromium --grep=@partner
```

Потрібні встановлені браузери (`npx playwright install chromium firefox webkit`)
і вільний 4173. Останній запуск використовує лише dedicated E2E persistence.
[CLI E2E](../tests/smoke/partner-cli.spec.ts) відтворює цей шлях, перевіряє
1/1/1/1/1/1/2 у звіті, незмінність даних від повтору й читання, відсутність
зовнішніх посилань-переходів. [SC-14 Worker](../tests/worker/report.test.ts)
доводить точний ClickID, пізні/майбутні результати, межі дня, причинні
посилання, порожній період і незалежність quiz від offer-фільтра.
[History Worker](../tests/worker/report-history.test.ts) доводить явне
підтвердження та сталість доступних чисел після справжнього cleanup.
[Delivery Worker](../tests/worker/delivery.test.ts) і
[Maintenance Worker](../tests/worker/maintenance.test.ts) покривають
відмови приймача, ACK/lease, backoff та технічні попередження.

Реалізовано локально й розгорнуто у M6: квіз/API v1, атомарні команди й повтори, ClickID,
Lead/Purchase, read-only Basic Auth звіт, retention і фоновий протокол.
Партнера імітує CLI, приймач — таблиця D1; зовнішня доставка до BigQuery
не відбувається. Назва/URL офера показуються без реального переходу,
email синтетичний і листів немає. BigQuery, production-масштаб,
автоматичний EPU та виключення за Purchase залишаються в дизайні.
Хмарний adapter, deploy/smoke, реальний Cron і recovery підтверджено
окремим [звітом M6](m6-release-result.md); це не гарантія production-навантаження.
Реальний restore не виконувався, мобільна матриця — лише емуляція Playwright.
