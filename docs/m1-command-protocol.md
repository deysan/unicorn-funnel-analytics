# M1 — атомарний запис команд і місткість

Стан на 2026-10-31: внутрішній протокол реалізовано на локальній D1.
Це продовження [схеми й результатів](m1-data-model.md). HTTP-команди,
конкретні правила кроків/вибору офера/Lead і Cron підключатимуть цей шар
у M2–M4; самі helpers не означають готовий бізнес-сценарій.

## Порядок запису

`executeCommand` приймає нормалізовану команду, серверний hash секрету
доступу, HMAC keyring, годинник та внутрішній builder SQL-ефектів.

1. Перевіряє доступ профілю: hash, revoked_at, expired_at, логічні 180 діб.
   Читає replay: found/conflict/expired повертаються без нового резерву.
2. Читає профіль із revision; builder обчислює результат і потрібні SQL.
   Команда клонована й заморожена на запит; OperationID/payload незмінні.
3. Читає epoch потрібних бюджетів. Готує результат, потім бере свіжий
   серверний час для access/TTL та callback перевірок залежностей.
4. Один batch: access → revision → доменні references → integrity/control
   → всі потрібні epoch → місткість → резерви → бізнес-ефекти → activity
   → INSERT результату → видалення власних службових guard-рядків.
5. Невдалий guard або пізня SQL-помилка відкочує весь batch. `changes()`
   перевіряється відразу після кожного ефекту. Guard-рядків після успіху немає.

Builder є довіреним серверним кодом: він задає точні прирости events/
undelivered, очікувані changes(), доменні SQL та references. Executor
завжди додає один command_keys. SQL ніколи не береться з HTTP. Відбір
бізнес-полів для HMAC, валідація DTO та конкретні step/selection помилки
належать handlers, а не цьому універсальному шару.

Приріст revision при фактичній зміні вподобань/email/Lead і деактивації
належить SQL конкретних мутацій за D-161; executor перевіряє snapshot,
але не збільшує revision за сам факт команди. Поновлення last_active_at
використовує MAX і не змінює revision. Повернення replay activity не поновлює.
Каталог майбутнього builder має бути незмінним у межах одного запиту.

## Повтори та помилки

Після відмови batch ще раз перевіряємо доступ і збережений результат.
Знайдений відповідний результат повертається навіть після втрати відповіді
на успішний commit. Конфлікт і expired не стають новою командою.

Лише розпізнаний `guard_revision` дозволяє нове обчислення: до трьох
спроб запису для question_view/answer/email_confirmation/offer_selection.
Entry автоматично не повторюється. Після третьої відмови — останнє читання
результату, без нього temporary. Epoch, невідомий результат, SQL/network
помилка, access/reference/integrity/capacity не запускають цей цикл.

Класифікатор приймає лише відомі іменовані CHECK у перевіреному форматі
D1, включно з `SQLITE_CONSTRAINT (extended: SQLITE_CONSTRAINT_CHECK)`.
Довільний substring, вкладена cause або невідома назва не є доказом.
Непізнаний формат безпечно дає temporary; він потребуватиме звірки після
оновлення runtime. Сирі SQL-повідомлення й payload не повертаються.

## Чотири бюджети

| Бюджет | Ліміт | Відновлення нижче |
|---|---:|---:|
| undelivered | 1000 | 800 |
| events | 10000 | 8000 |
| profiles | 1000 | 800 |
| command_keys | 20000 | 16000 |

`reserveCapacity` додає guards і резерви до `GuardedBatch`. Нульовий приріст
не перевіряє capacity pause цього бюджету. No_offer витрачає тільки ключ.
Потрібний відсутній/непридатний control — технічна відмова, не нуль.
Усі epoch перевіряються до будь-якої відмови місткості; застарілий snapshot
не встановлює pause. Успішне досягнення рівно limit ставить pause разом
із бізнес-ефектами. Переповнення одного бюджету відкочує решту резервів.

Після доведеної відмови й перевірки конкурентного результату виконується
окремий awaited `persistCapacityPause`: лише для того самого epoch і count
не нижче порога відновлення. Старий цикл — no-op, integrity не змінюється.
Збій цього запису — temporary. Падіння між транзакціями може не залишити
pause; верхню межу все одно захищає кожний новий batch (D-163).

`releaseCapacity` додає decrement, зняття pause нижче порога й приріст
epoch при переході ≥80% → <80% до batch caller. Caller мусить
додати фактичний ACK/delete та guard кількості змін. Тести імітують ефект
доставки; повний lease/ACK-протокол не реалізовано цим helper.
Повтор без фактичної зміни не має віднімати count. Tombstone ключа не
звільняє місткість. Integrity pause блокує також release; автообнулення
або перерахування лічильників немає. Звірка й ручне відновлення — M4.

## Перевірки та межі

39 Worker/D1-тестів протоколу: конкурентний ключ; revision 1–3 спроби та
останній winner; unknown outcome із/без commit; access/TTL/references;
пізня integrity pause; чотири точні межі; переповнення без часткових
резервів; старий epoch; delayed pause після drain/refill; збій службового
запису; release із rollback/повтором та незалежне відновлення бюджетів.
Порогові тести задають синтетичні counts — це не доказ reconciliation.

Підсумковий локальний `CI=true npm run check`: **96 Vitest** (18 unit +
78 Worker), типи, збірка та **21 Playwright** пройшли. Браузерна матриця
поки перевіряє каркас M0. GitHub CI перевірив попередній M0, не ці зміни.

Незалежне BMAD Build рев’ю перевірило протокол, схему й тести за
погодженими рішеннями; доказових дефектів не виявлено. Рев’юер читав
тести, але не запускав їх повторно.

Пізніший [аудит усього M1](bmad/reviews/2026-10-31-m1/report.md) додав
регресійні перевірки готового replay після revoke/hash/TTL та entry без
автоматичного revision-retry. Обидві прогалини закрито до коміту M1.

Виправлено помилку незакоміченої `0002`: expired stub більше не вимагає
revision=0; тест деактивації зберігає наступну версію 4 → 5 за D-161.
`0003` додає guards control/integrity/epoch/кожного бюджету.
Міграції застосовувалися лише до ізольованих тестових D1.

Один DELETE прибирає всі власні guard-рядки наприкінці batch, щоб не
додавати окремий DELETE на кожну перевірку. Кількість SQL і ресурсів
конкретних HTTP-команд ще треба звірити після їх реалізації; це не
benchmark чи доказ відповідності хмарним квотам Free.
