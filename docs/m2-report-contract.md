# Контракт базового закритого звіту M2

> Межі цього документа: етап станом на 2026-11-01. Проміжні статуси й
> результати нижче — історія відповідного етапу. Актуальний підсумок M0–M6:
> [хмарний реліз](m6-release-result.md), [план](plan.md).

Дата: 2026-10-31. Конкретизація погоджених D-013/014/022/045/046/053,
D-086/087/104/105/114–116/143–155. Джерело істини — requirements/decisions.
Це локальний наскрізний звіт M2; Cron/cleanup та експлуатаційне підтвердження
повноти після restore лишаються M4/M5. Нових бізнес-рішень немає.

## Читання та доступ

- `/report/` (і `/report`) та `/api/v1/report/*` захищені серверним Basic
  Auth; HTTPS, no-store, без секретів у bundle/URL/логах. Звіт read-only,
  не поновлює cookie/профіль і не запускає Cron. Окремі локальні credentials
  генерує setup у ignored .dev.vars лише за відсутності. Публічний квіз
  і партнерська Bearer-авторизація лишаються незалежними.
- IP limiter 300/min перед auth, спільний report scope 30/min після auth;
  наявний fail-closed local IP adapter, 1s сумарного очікування, паузи
  60/30s. Не змінювати локальні ліміти для тестів. Cloud adapter — пізніше.
- GET `/funnel`: обов’язкові from/to, включні UTC YYYY-MM-DD, календарно
  правильні, from<=to<=сьогодні. Опційні одиничні preland_id/offer_id
  за чинними форматами каталогу. Порожні/повторні/невідомі параметри,
  масиви/час замість дати відхиляються. Початкові нулі ID зберігаються.
- Один параметризований SELECT D1 для бізнес-чисел, метаданих і часу
  зрізу; не читати весь журнал для агрегації в Worker. Межі днів —
  [from, to+1day). Зріз не обмежує результати когорти occurred_at<=now.
- GET `/status` без query: власний updated_at, реальні поточні delivery
  counts, бюджети/паузи/integrity/history flags. Не імітувати роботу Cron
  або успішний експорт: вони ще не реалізовані. GET `/filters` без query:
  поточні active/inactive offers + historical ID із clicks/events, demo
  та збережені prelands, sorted unique, власний updated_at; один зріз
  збережених ID, одна версія каталогу. Не видавати EPU/URL/профілі.

## Бізнес-метрики

`metrics.quiz` і `metrics.offers` містять `activity` та `conversions`.
Activity — незалежні унікальні UserID за occurred_at у періоді:
входи, початки (будь-який показ питання), покази/підтвердження кожного
з трьох питань, завершення (email answer_confirmed), переходи на офер,
переходи bypass, Lead, покупці; покупки — окреме число Purchase.
Quiz фільтрується лише preland/date, offers додатково offer. Ніяких сум
унікальних користувачів між прелендами/оферами. Старі/неактивні офери
не виключаються. Журнал events — джерело метрик, не profile/compact Lead.

Конверсії — точні `{numerator, denominator}` унікальних UserID однієї
групи. Період визначає вхід; результат враховує всі прийняті події зрізу,
також пізні та допустимо майбутні партнерські timestamps.

- Показ питання → підтвердження: користувачі з показом питання в періоді;
  подальше підтвердження того самого питання після першого такого показу
  у вибраному зрізі. Перевірений view_event_id має відповідати user/preland/
  question та часовому порядку; прогрес може йти через повернення, не
  вимагаємо одного entry або показу лише всередині початкового періоду.
- Початок → завершення: від першого показу будь-якого питання користувача
  в періоді; подальше email confirmation з валідним зв’язком із показом.
- Початок → будь-який офер: та сама група; quiz transition із конкретним
  completion_event_id відповідної подальшої email confirmation. Bypass
  не зараховується, фільтр offer цей показник не змінює. A/B можуть мати
  різні entry; не перетворювати entry_event_id на VisitID.
- Перехід → Lead/Purchase: користувачі з переходами у періоді;
  результати лише ClickID саме цих переходів. Старий Lead іншого click
  не конвертує новий, Purchase не потребує Lead. Кілька покупок одного
  користувача не множать numerator. Рівні timestamps допустимі при
  правильних причинних посиланнях.

UI: 0/0 — «немає даних», 0/N — 0,0%; округлює до одного знака. Для
питань окремо «ще не підтвердили» = denominator−numerator. Пара поза
0<=numerator<=denominator — технічна помилка, не clamp/ready.

## Повнота історії

ready містить metrics/available_from/updated_at/filters. unavailable —
HTTP200 з reason/updated_at/filters, без metrics. history_unverified
переважає period_unavailable й не містить available_from. Друга причина
містить available_from; період не обрізаємо. За відсутніх/суперечливих
метаданих — технічна недоступність без чисел; явно unverified — відповідний
стан. Порожній доступний період має нулі.

`available_from = max(підтверджена початкова/консервативна межа,
початок строго наступної UTC-доби після дати(now−90days+5min))`.
Не використовувати MIN(events), факт порожніх таблиць або deploy як доказ.
Коментар міграції 0002 про перший бізнес-запис не відповідає D-114;
міграцію не переписувати, це зафіксований залишок каркаса, який усуваємо
до нового запуску через явний provisioning нової історії. setup перед
міграціями може встановити доказ створення нової persistence (до цього
D1 storage відсутня); E2E має явний reset лише dedicated test state.
Після міграцій і ДО запуску сервера новій доведено створеній базі атомарно
ініціалізувати UTC-день; guarded initializer не працює на базі з бізнес-
даними/попередніми метаданими. Звичайний запуск старої бази не backfill,
не очищає і не знімає unverified. Restore/reset існуючої історії потребує
окремої перевірки; цей підкрок її не вигадує. Worker fixtures задають
підтверджені метадані явно. Читання звіту не ініціалізує історію.

## Інтерфейс

Окрема сторінка, назви й пояснення українською. Default from=to=UTC day
із status.updated_at, поточний день позначено незавершеним. URL — джерело
застосованих фільтрів; replaceState, не нові Back entries. Форма локальна
до «Застосувати», незастосовані зміни позначено. Invalid URL не скидається
мовчки: виправлення або явний reset. Відсутні в filters вибрані ID видимі.
Помилка filters не блокує funnel із явними датами; старий список позначено.
Після початкового періоду status/funnel незалежні.

Ручне оновлення читає всі три endpoints, auto — funnel/status через60s
після завершення попередньої спроби лише у видимій вкладці, без overlap.
Пауза limiter також дотримується; мережеві помилки не викликають tight loop.
Запізніла відповідь старого вибору не змінює новий звіт. Помилка/unavailable
прибирає бізнес-числа, не видає попередні за свіжі. Не зберігати auth у JS.

## Перевірка

Unit: суворі query/DTO/час/відсотки. Worker: SC-14, міжденні когорти,
перепройдене питання, однаковий час, точний ClickID, bypass, future-time,
retention midnight, missing/unverified metadata, порожній період, auth,
rate-limit failures, no writes/cookies, filters historical IDs. Browser:
захист HTML/API, квіз+Lead+bypass+2 Purchase+повтор→правильний звіт,
URL/reload/invalid/filters, unavailable/error без старих чисел, stale
responses/visibility/refresh; desktop/mobile критичний шлях.

Технічне джерело перевірено 2026-10-31:
[Worker-first assets](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)
— `/report` і `/report/*` через Worker auth до ASSETS.fetch; API — чинний маршрут.
