# Експлуатаційне підтвердження історії звіту

Дата: 2026-11-01. Локальний операційний пакет M5 за D-098/D-116.
[Контракт звіту](m2-report-contract.md), [retention і звірки](m4-retention.md),
[прийняті рішення](decisions.md). Описана процедура не означає, що restore
або SQL проти наявної dev/хмарної бази виконувалися. Хмарне відновлення
та перевірка можливостей провайдера належать окремій погодженій операції.

## Коли бізнес-числам не можна довіряти

Виявлена втрата/позапланове видалення або неперевірений restore вимагає
`history_unverified=1`. Звіт повертає HTTP 200, `report_status=unavailable`,
`reason=history_unverified`, без `metrics` і `available_from` для всіх періодів.
Технічний стан доступний окремо, якщо його вдалося прочитати.
Відсутня або некоректна початкова межа без прапорця недовіри — технічна
недоступність, а не порожній звіт. Читання нічого не ініціалізує.

Наявність подій, `MIN(occurred_at)`, нульові таблиці, новий deploy, поточний
день або успішні Cron/звірка не доводять повноту. Наявна dev-історія
не визнається повною без зовнішнього доказу. Не видаляйте persistence
і не використовуйте `newHistorySql` для ремонту старої бази: initializer
призначений лише для доведено нової persistence до першого запуску.

## Зупинка й діагностика

1. Зафіксуйте причину сумніву, цільову базу/середовище, версію коду й міграцій,
   час інциденту та межі відомих прийнятих записів. Не копіюйте payload,
   email, токени, заголовки авторизації чи повні профілі в журнали.
2. Перед restore встановіть **зовнішній режим обслуговування**: зупиніть
   надходження квіз-команд і постбеків, Cron, доставку та cleanup; закрийте
   бізнес-звіт. У localhost зупиніть усі dev/preview процеси та CLI send;
   у хмарі потрібне окреме блокування трафіку й scheduled запусків поза
   відновлюваною D1. Дочекайтеся завершення запитів/ACK у польоті.
   Прапорець у D1 не є таким блокуванням: restore може відкотити його.
3. До restore явно позначте історію недовіреною. Restore допустимий лише
   після окремого погодження й оцінки новіших прийнятих записів, які він
   може втратити; цей пакет не виконує restore та не містить його команди.
4. **Після restore знову встановіть недовіру**, перш ніж відкривати будь-яке
   читання бізнес-звіту: старий `history_unverified=0` не є доказом.
   Під час усієї діагностики та підтвердження заборонені конкурентні
   операційні зміни, restore, міграції й інший оператор підтвердження.
5. Перевірте сумісність схеми 0001–0005 з кодом, причинні посилання
   подій (entry/view/completion/ClickID), ключі й результати повторів,
   партнерські ключі, delivery/lease/ACK, компактні Lead та поточні TTL.
   Restore може втратити дедуплікаційні ключі; автоматичного злиття немає.
   Лічильники звірте з фактичними рядками одним узгодженим читанням за
   правилами [M4](m4-retention.md). Не «виправляйте» counters заради green status.
6. `integrity_paused=1` забороняє підтвердження історії. Діагностика причини
   й окреме погоджене поновлення цілісності за D-166 передують цьому кроку.
   Жоден helper нижче не знімає integrity/capacity пауз, не рухає epoch,
   не змінює counters, бізнес-рядки або TTL.

Безпечний мінімум для перечитування metadata (без персональних даних):

```sql
SELECT singleton_id, history_available_from, history_unverified, integrity_paused
FROM system_control WHERE singleton_id = 1;
SELECT budget_key, used_count, capacity_paused, capacity_epoch
FROM capacity_control ORDER BY budget_key;
```

## Доказ і консервативна межа

Оператор має довести або відсутність впливу інциденту на доступне вікно,
або безпечний початок після прогалини. Зіставте інцидент/restore з відомими
прийнятими операціями та причинними зв'язками: недостатньо мати всі входи,
якщо втрачено подальший completion/перехід/Lead/Purchase для цих когорт.
Враховуйте пізні партнерські результати та їхню атрибуцію до точного ClickID.
Сам відновлений журнал не є незалежним доказом відсутності зниклих подій.

Підтверджена межа — цілий UTC-день у мілісекундах Unix, не майбутній,
не раніший за вже встановлену `history_available_from`. Якщо безпечна
межа припадає всередині дня, беріть наступний цілий UTC-день; якщо він
ще майбутній або доказу бракує — залишайте недовіру. Не обирайте
«сьогодні» автоматично. Відсутню початкову межу (`NULL`) можна встановити
лише після того самого зовнішнього доказу.

Фактична доступність звіту лишається:

```text
max(підтверджена межа,
    початок строго наступної UTC-доби після дати(now − 90 днів + 5 хвилин))
```

Запит до цієї межі повертає `period_unavailable`; сервер не обрізає період.
Звичайний retention може рухати межу вперед, не знімаючи недовіру.

## Генератори SQL та перевірка результату

[scripts/report-history.ts](../scripts/report-history.ts) **лише генерує SQL**.
Немає нового HTTP/admin API або автоматичного виконання. Нижче команди
для оператора після діагностики; під час M5 їх не виконували проти dev D1.
Node 24.22.2 запускайте з кореня репозиторію. Генерація недовіри:

```sh
node --input-type=module -e 'import { markHistoryUnverifiedSql } from "./scripts/report-history.ts"; console.log(markHistoryUnverifiedSql())'
```

Це один ідемпотентний UPDATE лише `history_unverified=1` з `RETURNING`.
Він працює також із відсутньою/зіпсованою межею та вже активною integrity
паузою. Нуль повернених рядків означає відсутній singleton: зупиніться
й діагностуйте схему; не вставляйте «здоровий» control рядок навмання.

Для підтвердження перечитайте metadata під зовнішнім блокуванням і
підготуйте ignored `.wrangler/report-history-evidence.json`:

```json
{
  "confirmed_from": "ЗАМІНИТИ_НА_ДОВЕДЕНІ_ЦІЛІ_МІЛІСЕКУНДИ_UTC",
  "expected": {
    "history_available_from": "ЗАМІНИТИ_НА_ПРОЧИТАНЕ_ЧИСЛО_АБО_null",
    "history_unverified": 1
  }
}
```

Це шаблон, який навмисно не проходить валідацію. Замініть рядки на JSON
числа або `null`, а прапорець — на фактично прочитане `0`/`1`. Файл містить
тільки технічну межу/очікування; докази та рішення оператора фіксуються
окремим безпечним записом інциденту, без персональних даних.

```sh
node --input-type=module <<'JS' > .wrangler/report-history-confirm.sql
import { readFileSync } from 'node:fs';
import { confirmHistorySql } from './scripts/report-history.ts';
const evidence = JSON.parse(readFileSync('.wrangler/report-history-evidence.json', 'utf8'));
console.log(confirmHistorySql(evidence.confirmed_from, evidence.expected));
JS
```

Якщо генератор завершився з помилкою — не виконуйте файл. Перегляньте
SQL: один guarded UPDATE з точним порівнянням обох очікуваних history
полів (`IS NULL` для відсутньої межі), `integrity_paused=0`, забороною
руху межі назад та перевіркою майбутнього часу також під час виконання
D1. Приклад **лише локального** виконання вже перевіреного файла:

```sh
npx wrangler d1 execute unicorn-local --local --persist-to .wrangler/state --file .wrangler/report-history-confirm.sql
```

Дивіться саме рядок `RETURNING`, а не лише exit code або `success:true`:
має бути **рівно один** рядок з очікуваною межею, `history_unverified=0`,
`integrity_paused=0`. Нуль рядків — відмова, жодного поновлення. Перечитайте
metadata й заново перевірте докази; не замінюйте WHERE на безумовний UPDATE.
CAS не виявляє зміну й повернення тих самих значень (ABA), тому не замінює
зовнішнє блокування або заборону конкурентних операцій.

Перечитайте controls та переконайтеся, що counters, паузи/epoch збережено.
Перевірте звіт: доступний період `ready`, старіший — `period_unavailable`
без `metrics`; за недостатнього доказу лишається `history_unverified`.
При будь-якому новому сумніві знову встановіть недовіру. Зняття зовнішнього
режиму обслуговування — окремий крок після перевірки TTL, усіх залежностей
і чинних пауз; саме підтвердження історії не дозволяє записи/доставку.

## Відтворення локальних доказів

```sh
npm run test:worker -- tests/worker/report-history.test.ts tests/worker/report.test.ts tests/worker/maintenance.test.ts tests/worker/maintenance-audit.test.ts
npm run typecheck
```

[Тести історії](../tests/worker/report-history.test.ts) виконують згенерований
SQL у справжній ізольованій D1. Є stale metadata, future/non-day, відсутня
межа, integrity/capacity паузи, незмінність інших таблиць, реальний
production Cron/cleanup та нові квіз/партнерські факти. Тести не виконують
restore, не читають dev persistence і не доводять повноту наявної dev-бази.
