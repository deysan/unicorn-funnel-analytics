# M4 — обмежена діагностика одиничного Q1 503

Дата: 2026-11-01. Статус: **готово до фінального аудиту M4**, без коміту.
Причину інциденту не встановлено; виправлення не приписуємо.

## Доручення й виняток

Власник доручив дослідити попередній 503 перед фінальним аудитом і явно
дозволив пропустити одиничний інцидент, якщо причина лишиться невідомою:
«Якщо це було разово, то думаю можемо пропустити якщо причина невідома».
Цей дозвіл застосовано **лише до вже зафіксованого timeout CLI-тесту після
generic 503 на початковому Q1 view**. Загальне правило D-111 не змінюється:
нові або повторювані збої обов'язкових тестів знову потребують діагностики.
Виняток дозволяє перейти до фінального аудиту, а не оголосити весь M4
завершеним чи виконати commit/deploy.

## Збережені докази

Read-only перегляд архівної синтетичної D1 підтвердив 100 профілів, одну
подію funnel_entered, один результат entry та нуль transaction_assertions.
Лічильники: profiles=100, events=1, undelivered=1, command_keys=1;
усі capacity_epoch=0, паузи відсутні. Доставка entry була pending,
attempt_count=0, lease/ACK відсутні. Виконана доставка Cron не пояснює збій.

Профіль створено за 5589 мс до entry. Час події та результату entry
однаковий; last_active_at на 3 мс пізніший. Отже, fixture setup завершився
до першого бізнес-запису; порушення created_at/last_active_at у збережених
даних немає. Архів не містить внутрішньої помилки Q1, тому відсутність
запису не розрізняє read/build/batch failure або rollback.

## Перевірені гіпотези

| Гіпотеза | Перевірка | Висновок |
|---|---|---|
| Одна мілісекунда entry/Q1 або рух commit clock на −1 мс | Код використовує спільний build-time для події/результату; свіжий entry не потребує строго меншого часу; activity записується через MAX. Три ізольовані D1 cases: однаковий час, commit−1 мс, архівні +5589/+3 мс | Усі прийняті, counters/guard rows узгоджені; дефект не відтворено |
| Гонка revision/epoch, невідомий commit, частковий запис | Прочитано executor/guards; повторно виконано наявні quiz/command-protocol тести конкурентних ключів, revision retries, epoch, rollback і unknown commit | Перевірки пройшли; архів не має evidence такої гонки саме в інциденті |
| Rate limiter або штатна відмова доступу | HTTP mapping дає їм окремі коди; generic temporary охоплює невідомі помилки читань/build/batch | Звичайна відмова limiter/access не відповідає зафіксованому generic повідомленню; невідома runtime/D1 помилка можлива, але не доведена |
| Нестабільний UUID/fingerprint/catalog | Окремий investigator прочитав нормалізацію, schema та lazy catalog; Q1 бізнес-поля не містять часу | Конкретної відтворюваної причини не знайдено |

Окремий investigator працював read-only в незалежному контексті, без
попередньо заданої причини; тестів сам не запускав. Його висновок —
причина невідома, не заявляти вигаданий runtime-дефект.

## Фактичні перевірки та межі

Один bounded запуск: **84/84** — 81 наявний quiz/command-protocol тест
і 3 тимчасові clock cases. Node 24.22.2, ізольована локальна D1.
Лог `/tmp/unicorn-q1-bounded-diagnostic.log`; тимчасовий source збережено
поза репозиторієм як `/tmp/unicorn-q1-incident-diagnostic.test.ts` і прибрано
з test suite. Production-код не змінювався, instrumentation не залишено.

Попередні 294 Q1 діагностичні проходи не повторювали. Після інциденту
вже пройшли повні retention checks: 496 Vitest + 89 Playwright та після
review fixes 503 Vitest + 89 Playwright, обидва з CLI 2/2. Це не доказ
виправлення причини, але нового evidence постійної несправності немає.
Новий повний check лише після документаційної фіксації не потрібен:
production tree лишився тим самим, що у фінальному успішному прогоні.

Dev D1 та архів не змінювалися. Немає нових автоматичних retries,
послаблення assertions/timeouts, commit/push/deploy. Залишковий ризик
невідомої причини прийнято лише в межах явного одноразового дозволу.
