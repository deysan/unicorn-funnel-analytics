# M2 — каталог оферів і правила вибору

Історичний запис підкроку. Актуальний підсумок усього M2 на 2026-11-01 —
[фінальний аудит](bmad/reviews/2026-11-01-m2/report.md).

Стан на 2026-10-31: перший підкрок M2 реалізовано. Це серверні чисті
правила й конфіг, без HTTP-команд, запису ClickID або нового UI.
M1 зафіксовано в `2c6798642ff5740f742246d2de8fdc6f16542e9c`.

## Каталог

`src/server/offers/config.ts` містить початкові сім оферів із ТЗ:
ID, назва, етніка, genders, epu_usd, active, partner_id та url.
Усі початково активні. Один `demo-partner` — синтетичне зіставлення для
демо, не твердження про реальні інтеграції. Секретів у конфігу немає.
Зміни проходять через Git і нове розгортання за D-028.

`createOfferCatalog` суворо перевіряє весь об’єкт через Zod. Невідоме
поле, неправильний тип, повтор ID, невідомий партнер чи неправильний URL
дають лише безпечний `catalog_invalid`; офери не пропускаються мовчки.
Допускаються підмножини початкових ID 001–007 та порожній список для
сценаріїв вилучення/відсутності оферів. Початкові значення перевірено
окремим тестом проти ТЗ; універсальним fallback є тільки 007.

EPU — скінченне невід’ємне число USD без округлення до центів. Сума
Purchase до цього поля не має стосунку. Формат partner_id та OfferID
перевіряється без trim/lowercase виправлень. Назва непорожня після
перевірки пробілів, зберігається без обрізання, до 256 байтів UTF-8.

URL має HTTPS, без credentials, сирих пробілів/control/backslash.
Наявний query click_id відхиляється, включно з регістром декодованого
імені. `buildOfferUrl` додає рівно один click_id із UUID v4, зберігає
семантику статичних query та fragment і перевіряє готові 2048 байтів.
Параметрів користувача цей helper не приймає. Відкриття URL не виконує.
Перевірка конфігу використовує синтетичний UUID такої самої довжини.
Персональні дані/секрети в статичних значеннях заборонені правилами
репозиторію; валідатор не є універсальним детектором їхнього змісту.

## Незмінний snapshot та version

Валідатор створює копію й глибоко заморожує каталог. Офери сортуються
за ID, partners та множини genders — лексикографічно; URL нормалізується
через URL.href. Версія — SHA-256 UTF-8 JSON такого формату:

```text
["unicorn.catalog", 1, partners, [
  [id, name, ethnicity, genders, epu_usd, active, partner_id, url], ...
]]
```

До хешу входять усі дозволені поля, але не сам version. Перестановка
оферів/полів/множин і форматування не змінюють версію; зміна значення —
змінює. Версія початкового каталогу:
`3bedf13e48229522c7973558183f9a9c77fcddeca0b819177010522d5a787cd8`.
Незалежний вектор обчислено через node:crypto і звірено з Web Crypto
в Node та локальному workerd.

`getOfferCatalog` ліниво створює й кешує одну пару snapshot/version.
Немає автоматичного повернення до старого конфігу при помилці. Vite
викликає той самий валідатор до dev/build; наявний CI виконує unit/build.
Майбутня команда B викликає getter всередині builder після перевірки
replay і тримає один snapshot на запит. B вже підключено у
[наступному підкроці](m2-final-commands.md);
старі збережені результати M1 зараз не змінювалися.

## Вибір і повернення

`selectOffer` працює тільки з валідованим каталогом та переданим станом:

1. Серед Lead активних оферів — найбільший registeredAt, при рівності
   найменший OfferID. EPU та вподобання не впливають на цей пріоритет.
2. Без активного Lead потрібні обидва допустимі вподобання; інакше
   needs_quiz. Неповний профіль не потрапляє на 007 автоматично.
3. Серед активних спеціалізованих збігів — максимальний EPU, при рівності
   найменший ID. 007 виключений із цього порівняння.
4. Без спеціалізованого збігу — активний 007, інакше no_offer.

Відсутній у поточному каталозі офер не стає кандидатом. Час Lead —
перевірений час реєстрації, не отримання постбека. Caller має передати
тільки чинні компактні Lead цього профілю; їх завантаження/TTL належать
наступному шару. Email і Purchase не є входами selector.

`returningUserAction` окремо повертає quiz/select_offer: активний Lead
або збережений Lead недоступного офера + повні вподобання дають
select_offer за D-023/D-136. Самі відповіді без Lead лишають quiz.
Підказка не замінює перевірок B: новий вибір може дати no_offer.

## Перевірки й наступний крок

63 нові unit-випадки та 3 Worker-перевірки покривають початкові дані,
шість комбінацій, Lead/EPU ties, inactive/removed, fallback/no_offer,
неповні вподобання, bypass, валідацію, URL-байти та стабільність version.
Повний `CI=true npm run check`: **162 Vitest** (81 unit + 81 Worker),
типи, збірка та **21 Playwright** пройшли локально. Браузерні тести
поки перевіряють каркас, а не новий квіз. Deploy/міграцій/коміту немає.

Незалежний BMAD Build рев’юер прочитав код і тести та звірив їх із ТЗ
і рішеннями; підтверджених дефектів не виявлено. Тести він сам не запускав.

Наступний підкрок виконано: [читання стану профілю/Lead і перші команди
квізу](m2-quiz-commands.md), а також [A/B і ClickID](m2-final-commands.md).
Перший наскрізний HTTP/UI-сценарій M2 ще попереду.
