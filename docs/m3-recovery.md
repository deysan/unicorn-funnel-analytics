# M3 — відновлення й захист

2026-11-01. Етап завершено локально після M2 (`6a67795`).
Погоджені бізнес-рішення незмінні. [Підсумковий BMAD-аудит](bmad/reviews/2026-11-01-m3/report.md)
закрив матрицю SC-03–09/13; власник дозволив один коміт за результатом.
Нижче збережено хід підкроків і фактичні перевірки кожного.

## Перший підкрок: невідома відповідь API

За D-069/D-124 і SC-09 невідома відповідь не доводить втрату доступу.
Раніше JSON null породжував TypeError і хибне повідомлення про локальне
сховище; неповний identity_lost міг очистити чернетку. Клієнт тепер
перевіряє envelope до використання code. Некоректна відповідь дає
ручний retry зі збереженням ключів; валідні помилки зберігають поведінку.

Доказ: unit-таблиця malformed/HTML/valid errors; browser-сценарій
із реально записаною A та підміненим error response. Повтор читає A
за тим самим OperationID, не надсилає A вдруге; B створюється один раз,
ключі A/B незмінні, email зникає з чернетки після підтвердження.

## Другий підкрок: пізні відповіді контексту

За D-124 пізній success/error не змінює іншу дію або екран. Visibility
probe перевіряє покоління екрана, власний порядковий номер та ключ B
перед будь-якими ефектами. Читання API не оновлює clock до цієї перевірки.
Нова дія, приховування чи новий probe інвалідовують попередній; busy та
Retry-After не запускають додаткового GET. Локальна перевірка TTL працює.
Чинний контекст перевіряє доступ/власника й переплановує expiry без зміни
абсолютного дедлайну. Серверні команди не скасовуються.

Регресії: пізні identity_lost/429/success після готової B; відповіді
visibility у зворотному порядку; чинний час на межі TTL очищає email,
зберігаючи ключі; busy/paused не створюють конкурентного probe.
Незалежне рев’ю не виявило дефектів контролера. Зауваження про перетин
профілів між браузерами відкликано після перевірки runner: групи мають
окрему persistence, інші браузери виконують лише critical-піднабір.

Підсумковий check другого підкроку: **431 Vitest, 75 Playwright**
(32 Chromium + 24 матриця + 2 CLI + 13 report + 4 report matrix),
типізація/build — exit 0. Нових бізнес-рішень і коміту немає.


## Третій підкрок: дві вкладки й надходження Lead

Підтвердженого дефекту не знайдено, production-код не змінювали.
Додано чотири browser-регресії у `tests/smoke/concurrency.spec.ts`:

- Дві вкладки зі спільною cookie: зміна gender і ethnicity зберігає
  обидві відповіді; stale формулювання не синхронізується наживо;
  серверний men/europe обирає 005.
- R1 commit → втрачена відповідь → R2 commit → replay R1: той самий
  payload/OperationID не повертає старе значення.
- Перша затримана R1 приходить після R2: стає останнім записом;
  reload іншої вкладки читає актуальну відповідь.
- Реальний HTTP Lead для збереженого ClickID під час Q2 іншої вкладки:
  відповідь відхиляється як step_not_ready, поточні вподобання/UserID
  незмінні; явний refresh дає новий ClickID на 003 без нового email.

Worker/D1 вже перевіряє revision race, Lead між read/commit з rollback,
replay після Lead та переобчислення B. Браузерні сценарії доповнюють ці
перевірки; одночасний SQL commit імітують саме D1-тести. @concurrency
запускається окремою групою із чистою тестовою persistence, без зміни
реальних rate limits. Dev-дані не змінюються.

Підсумковий check третього підкроку: **431 Vitest, 79 Playwright**
(32 + 24 + 4 concurrency + 2 CLI + 13 report + 4 report matrix),
типізація/build — exit 0. Цільові 4/4 також пройшли; незалежне BMAD
Build рев’ю — без зауважень. M3 триває, коміту немає.
