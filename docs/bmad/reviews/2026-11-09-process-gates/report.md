# Перевірка правил готовності та підключення BMAD

Дата: 2026-11-09. Базовий HEAD: `f379ea326474e46fe99622cadbf8290e5003fa48`.
Перевірено локальний незакомічений пакет інструкцій поверх цього HEAD.

Доручення: внести погоджені зміни до AGENTS.md і BMAD, перевірити overrides
та контрольні сценарії. Код застосунку, коміт, push і deploy поза обсягом.
Це перевірка процесу, а не новий висновок готовності архітектури Unicorn.

## Підключення

Застосовано локальний `bmad-customize` та механізм team overrides.
Встановлені skills і runtime не редагувалися. Фактичний CLI resolver
успішно обробив усі три overrides; fallback до defaults не застосовувався.

| Workflow | Фактичний результат merge |
|---|---|
| bmad-architecture | Спільна рубрика, обов'язковий gate для суттєвих змін; 4 finalize-reviewers: 2 стандартні та R1/R2 |
| bmad-review | 7 lenses: усі 5 стандартних збережено, додано source-traceability і capacity-reliability; adversarial без квоти |
| bmad-build | Спільна рубрика й перевірка до маршрутизації; handoff із AGENTS і джерелами; 3 звичайні layers збережено, 1 oneshot layer; обидва Blind Hunter використовують R3 без квоти |

Build успішно згенеровано в snapshot
`_bmad/render/bmad-build/unicorn-ccf9a72e5352/6a551fb5f368a5447cdb/`.
Перевірено entry, маршрути dispatch/resume/oneshot, handoff та обидві
інструкції рев'ю. Нерозкритих workflow/snapshot-токенів немає.
Сам Build workflow не виконувався.

44 програмні перевірки пройдено: підтримувані поля, підключення рубрики,
збереження стандартних layers, унікальність їхніх ключів, відсутність
персональних overrides, активні no-quota recipes, порядок activation,
підстановки в snapshot і правила Git ignore. Runtime та `*.user.toml`
залишаються ignored; спільна рубрика та team overrides доступні для Git.

Під час перевірки встановленого runtime уточнено спільні правила:

- `spec is the sole source of truth` не скасовує вихідних вимог;
- resume/oneshot перевіряють актуальність доказів до залежної реалізації;
- помилка resolver/читання або невиконані R1/R2 означають INCOMPLETE;
- старий triage не закриває новий доказ, а помилка spec не є підставою
  відхилити суперечність джерелу;
- редакторський review і порожній findings-масив не замінюють gate.

## Контрольні сценарії

Вхід — [синтетичні сценарії v2](control-scenarios.md).
R1 (`/root/readiness_v2_r1`) та R2 (`/root/readiness_v2_r2`)
запущено в окремих контекстах без історії батьківського чату, очікуваних
відповідей і висновків одне одного. R1 зафіксував критерії за джерелами
до читання дизайнів. Обидва прочитали ту саму версію рубрики й входу.
Основний агент звірив докази та розрахунки після їхнього завершення.

| Випадок | Результат обох рев'юерів | Перевірений доказ |
|---|---|---|
| C1: цільовий потік і «відоме обмеження» | NEEDS_DESIGN | 50 × 86 400 / 300 = 14 400/добу проти 400 000; backlog +385 600/добу. Пік невідомий, але дефіцит є вже за середнього потоку |
| C2: історія не вміщується | NEEDS_DESIGN | 2 млн × 30 × 256 = 15,36 GB > 10 GB; обраного механізму розподілу/архіву немає |
| C3: шард за user_id | NEEDS_DESIGN | Один click_id на двох шардах проходить локальні UNIQUE: +2 замість +1 і конфлікту |
| C4: узгоджений модельний дизайн | READY_FOR_IMPLEMENTATION лише в межах P4 v1 | μ≥10/с > пік 2/с; backlog≤10; recovery≤1,25 с; видимість≤6,75 с. 411 SQL, ≤410 reads, ≤300 writes; БД 563 712 bytes |
| C5: звичайна описка | DELTA_CHECK_OK | Входи поведінкових доказів не змінилися; повного аудиту не потрібно |
| C6: недоступне джерело | INCOMPLETE | Матриця автора та ready-for-dev не доводять повноти без джерела |
| C7: resume після зміни вимоги | NEEDS_DESIGN | λ=25/с > μ≤10/с; backlog +15/с, або +1 296 000/добу; старий висновок непридатний |
| C8: R3 без дефектів | `[]` | Обидва контексти повернули порожні масиви без вигаданих зауважень |
| C9: пропущений R2 і fallback | INCOMPLETE | structure/prose та порожні findings не компенсують пропущені перевірки |
| C10: верхня межа швидкості producer | NEEDS_DESIGN | «До 10/с» не гарантує 10/с; швидкість БД не доводить швидкість повної доставки та заявлений recovery |

Усі 10 результатів фінального прогону відповідають контрольним очікуванням. C4 використовує
явно умовний контракт, а не вигадані виміри реального сервісу: готовність
дизайну не оголошена підтвердженою production-продуктивністю.

Перший прогін v1 мав пропуск: обидва рев'юери зарахували C4, де producer
обіцяв лише «до 10/с», а розрахунок використовував гарантовані 10/с.
Додаткова звірка `/root/delivery_architecture` виявила цю неоднозначність.
Після цього рубрику доповнено перевіркою найповільнішої ланки та відмінності
верхньої й нижньої меж; позитивний C4 отримав явну умовну гарантію,
а початкову проблему винесено в негативний C10. Усі сценарії повторено
двома новими контекстами. Початковий пропуск не зараховано як успішну перевірку.

## Відтворення та межі

Команди з кореня репозиторію для перевірки merge та render:

```bash
for skill in bmad-architecture bmad-review bmad-build; do
  uv run --no-cache _bmad/scripts/resolve_customization.py \
    --skill ".agents/skills/$skill" --project-root "$PWD" --key workflow
done
uv run --no-cache _bmad/scripts/render_skill.py \
  --skill .agents/skills/bmad-build --project-root "$PWD"
git diff --check
```

Згенерований workflow слід читати як результат перевірки підключення;
ці команди самі не запускають його реалізацію. Повтор семантичних сценаріїв
потребує двох чистих контекстів R1/R2 з тим самим входом; для C8 застосувати
R3. Порівняти відповіді з таблицею лише після завершення обох контекстів.

Overrides — інструкції для агента, а не програмне блокування Git або CI.
Прогони доводять підключення інструкцій і їх застосування до цих прикладів,
але не гарантують безпомилковості майбутніх AI-висновків. Повний запуск
Build/Architecture, новий аудит продукту, application-тести й cloud-перевірки
до цього обсягу не входять. Приватне листування не використовувалося
як вхід контрольних сценаріїв і не переносилося до репозиторію.

Фінальна звірка документації: 116 локальних цілей посилань існують;
`git diff --check` і перевірка whitespace також у нових файлах — без помилок.
Змінено лише 10 файлів інструкцій, налаштувань і документації, індекс порожній,
HEAD незмінний. Код застосунку, залежності, коміт, push і deploy не змінювалися
та не виконувалися відповідно до доручення.
