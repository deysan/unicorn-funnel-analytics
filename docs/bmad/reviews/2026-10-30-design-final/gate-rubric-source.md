## Знахідки

### RGS-01 — low — поточний реєстр вимог називає вже погоджені контракти відкритими

**Доказ.** `docs/requirements.md:160–162` після згадки D-051 каже
«Деталі API ще відкриті». Рядки 279–286 залишають механізми подій,
повторів, зберігання й retention майбутньому дизайну; рядок 296 узагальнює,
що API та конкретні механізми архітектурних гарантій ще деталізуються.
Водночас `docs/decisions.md:3116–3154` містить погоджені D-131/D-132,
`docs/architecture-notes.md:4622–4698` — групи маршрутів та точний склад
постбека, а spine AD-4–AD-14 задає механізми й межі гарантій. У
`docs/plan.md:44–45` бізнес-контракти вже названо визначеними.

**Наслідок.** Реєстр, оголошений джерелом статусу вимог, помилково створює
враження незакритого блоку бізнес/API-питань. Самої відсутності контракту
не виявлено; конкретні SQL/DTO та перевірки справді лишаються реалізації.

**Класифікація:** `autofix`. Оновити поточні статуси з посиланнями на
чинні D/P та M0–M5; відрізнити «визначено в дизайні» від «ще не
реалізовано/не перевірено». Не переписувати історію погоджень і не
позначати фактичну місткість чи результати тестів доведеними.

**Підстава:** узгодженість документації та AGENTS.md, а не нова вимога ТЗ.

## Рубрика good-spine

| Критерій | Висновок і доказ |
|---|---|
| Зафіксовано точки можливого розходження модулів | Так: ідентичність, вибір, атомарність, дедуплікація, причинність, A/B, атрибуція, бюджети, доставка, retention, звіт, auth, реліз і доказ завершення мають окремі AD-1–AD-16. |
| Rule придатне до перевірки та запобігає заявленому розходженню | Так на рівні дизайну; поінваріантна перевірка нижче. Відсутність коду не видається за пройдену перевірку виконання. |
| Deferred не залишає різної поведінки двом виконавцям | SQL/DTO/індекси мають стати спільним контрактом до залежних модулів (`spine:357–361`); M1 передує наскрізному M2. Неперевірені технологічні передумови блокують відповідний deploy, а не визначають альтернативну бізнес-поведінку. |
| Названі технології перевірено, точні версії не вигадані | Є датовані первинні джерела в platform-evidence/capacity. Версії кандидатів відділено від lockfile; остаточне pin і перевірка сумісності — M0 (`spine:331–334`). Це не мовчазний вибір `latest` для майбутнього коду. |
| Не суперечить brownfield | Реалізації немає; ратифікуються погоджені вимоги й D-001–D-179. Технічного brownfield-коду для звірки немає. |
| Покриває можливості вихідної специфікації | Так у межах фінального дизайну; матриця джерела наведена нижче. DEL-04/05/07 належать наступному етапу. |
| Не послаблює батьківські інваріанти | Окремого parent-spine у вході немає. Порівняння з успадкованими вимогами та D не виявило послаблення; зокрема D-163 явно обмежує атомарність паузи, не гарантію верхньої межі. |
| Немає цілком замовчаної архітектурної площини | Склад, дані, API, безпека, відмови, час, аналітика, ресурси, середовища, deploy, експлуатація, міграції та тести охоплені. Розміщення D1 лишається відкритою технічною деталлю D-016, географія й ціль вимірювання названі. |

| 4 | D1 batch, guard із CHECK/NOT NULL, revision і максимум три доведені конфліктні спроби | Не покладається на нуль UPDATE або SELECT перед записом як на атомарну гарантію. |
| 5 | Три явні простори ключів, unique у транзакції, fingerprint, строк результату й tombstone | Повтор не перезаписує відповідь і не створює нову покупку; конфлікт змісту окремий. |

| 7 | Окремі A/B, GET результату перед повтором, незмінний дедлайн, поведінка локальних збоїв | Успішна A не губиться через B; unknown outcome не перетворюється на скасування. |
| 8 | Історичний partner_id ClickID, спільний EventID, максимум occurred_at Lead, часові межі | Пізня доставка не переатрибутовує результат; Purchase без Lead і дві різні покупки визначені. |
| 9 | Чотири незалежні бюджети, атомарний резерв, 80/95/100%, epoch, integrity-пауза | Конкурентне перевищення заборонене; окремий запис паузи не маскується під спільний commit. |
| 10 | Lease/token, індивідуальний ACK, validation перед змінами, окремий commit приймача | Втрата ACK і stale attempt не подвоюють облік та не списують чужий backlog. |
| 11 | Логічні TTL, явні залежності, без cascade, pin потрібних рядків, фізичний count | Втрата деталізації не стирає чинний Lead; затримка Cron не подовжує право доступу. |
| 12 | Activity/conversions розділено; entry/ClickID cohort; numerator subset; offer-фільтр лише offers | Знаменники не змішуються з незалежними лічильниками; SC-14 відповідає правилам. |
| 13 | Один SELECT/as_of, явна межа available_from, unavailable без metrics, stale-response guard | Неповна історія не видається за нулі чи повний звіт. |
| 14 | Різні auth для груп, Origin/JSON, strictObject, no-store, конкретні 429/503 | Некоректний/чужий запит не має бізнес-ефектів; недоступний limiter не дозволяє bypass. |
| 15 | Окремі локальна й cloud D1, сумісна міграція перед Worker, ручний deploy, перевірка restore | Експлуатаційний вимір явно визначений; rollback даних не припускається автоматично. |
| 16 | Три рівні тестів, SC-01–14, блокування обов’язкових flaky-перевірок, scope README | Майбутні тести не названі виконаними; DEL-03 не розширює реалізацію. |

розбіжності. D-090/D-091 пояснюють різницю фізичних залежностей та
логічної чинності профілю. D-178/D-179 не змінюють Purchase-поведінку MVP.

## Відкладене та межі висновку

| Пункт | Класифікація | Чому не є пропущеною поведінкою фінального дизайну |
|---|---|---|
| SQL-міграції, конкретні guards/FK/індекси, DTO, порції Cron | `defer` до M0/M1/M4 | Правила, атомарні групи та очікувані наслідки вже визначені; спільна схема передує залежним модулям. Реалізація не доручена. |
| Остаточний lockfile/runtime/compatibility_date | `defer` до M0 | Є кандидат версій і датований доказ метаданих; build/typecheck/integration ще не виконані. |
| Free/$0 для rate-limit binding, ресурси акаунта/CI | `defer` до першого cloud use | platform-evidence §1 та plan:55–57 прямо забороняють трактувати невідоме як Free або автоматично брати Paid. Це не вимагає cloud setup під час поточного аудиту. |
| D1 placement | Відкрита технічна деталь D-016 | Площина географії не замовчана: узгоджене припущення та точки вимірювання є; без фактичного provision не стверджується конкретне розташування. |
| Фізичний byte-envelope target-буфера 1 млн, точний production SQL/ціна | Межа подальшого production-дизайну | D-018 — кількісна політика; capacity §2 дає потік/відновлення та обсяг історії, §1 — окрему оцінку малого демо. Жоден із документів не доводить фізичну місткість чи швидкість однієї Free D1 для target-потоку. Вимагати її реалізації або benchmark зараз означало б розширити D-026; якщо надалі потрібне production-рішення, ці оцінки не замінюють такого рішення. |

Проміжні результати не плутаються з фінальними: M2 названий наскрізним
зрізом, а не дозволом пропустити захист і відновлення; M6 залежить від
M3–M5. Джерело прямо не вимагає реального BigQuery, зовнішнього партнера,
адмінки, міграції чи production-масштабування в MVP (A:82,100–102).
Відсутність цих компонентів і невиконані навантажувальні тести не
зареєстровані як дефекти.

## Підсумок для triage

- **Autofix:** RGS-01 — актуалізувати статуси реєстру; RGS-02 — точні
  посилання на перенесені P-контракти.
- **Discuss:** нових обов’язкових бізнес-питань не встановлено.
- **Defer:** зберегти вже названі технічні/релізні передумови та межі
  майбутніх розширень, не оголошувати їх виконаними.
- **Gate:** готовий до фіналізації документації після редакційної звірки;
  фактична працездатність перевірятиметься лише в дозволеній реалізації.
