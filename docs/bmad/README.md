```bash
npx --yes bmad-method@6.12.4 install \
  --directory . --modules bmm --tools codex --no-shims --yes \
  --user-name ProjectOwner \
```

| Вхід BMAD | Наше джерело |
|---|---|

| Поточний етап і послідовність | `docs/plan.md` |

`docs/` залишається джерелом погоджених правил. Не створюємо другу незалежну
копію вимог лише заради шаблону BMAD. Звіти, пропозиції та допоміжні матеріали
BMAD зберігаємо в `docs/bmad/`; вони не змінюють вимоги автоматично.
Наявність документа не означає, що відповідний BMAD workflow уже виконано.

1. `bmad-help` використано для орієнтації; `bmad-review` — для початкового
   аудиту та перевірки сценаріїв окремими контекстами рев'юерів.
2. Після сценаріїв застосовуємо `bmad-prd` у режимі Validate до наявної
   розподіленої специфікації (вимоги + рішення + сценарії), без дублювання PRD.
   Артефакти перевірки — у `reviews/2026-10-29-scenarios/`.
   `bmad-architecture` розпочато в поступовому режимі; run workspace —
   `planning-artifacts/architecture/architecture-Unicorn-2026-10-29/`.
   Інваріанти зведено з погоджених D-001–D-179; фінальний gate пройдено.
3. План MVP зведено в `docs/implementation-plan.md`. За потреби детальні
   історії можна розкласти через `bmad-create-epics-and-stories` перед кодом;
   це не умова додавати нові бізнес-рішення до поточного дизайну.
4. `bmad-build` і тестові workflows — лише після явного переходу власника
   до імплементації. Перевірку готовності до реалізації зараз не оголошуємо пройденою.

Ролі Analyst, PM, UX Designer та Architect доступні в BMM для відповідних
обговорень. Рольова інструкція сама по собі не створює незалежного рев'ю:
у першому аудиті використовуємо окремі контексти агентів за двома методами
`bmad-review`, а не оголошуємо одного агента кількома незалежними експертами.

## Налаштування рев'ю

Для першого прогону обрано `adversarial` і `edge-case-hunter`: критичний
аналіз та пошук необроблених шляхів. Редакторські перевірки стилю не є метою
цього прогону. `verification-gap` орієнтований на код і тести, яких ще немає.

Офіційний adversarial prompt просить щонайменше 10 зауважень. Проєктний
override прибирає цю квоту: потрібні доказові зауваження, допустимий і порожній
результат. Інші налаштування вимагають української мови, конкретних прикладів,
врахування поточного етапу та відокремлення вже відкладених технічних питань.
Оригінальні skills не редагуємо; використовуємо механізм `customize.toml`.

Рев'юери не змінюють файли та не бачать висновків одне одного до завершення.
Основний агент перевіряє їхні твердження й позначає перекриття, вже враховані
питання та пропозиції. Нові бізнес-рішення обговорюємо з власником по одному.

## Фактична перевірка підключення

- Інсталятор завершився успішно: `core`/`bmm` 6.12.4, 29 skills, без legacy shims.
- Порівняння SHA-256 дев'яти наявних файлів до/після інсталяції показало:
  інсталятор їх не змінив. Резервний знімок зроблено локально до встановлення.
- `resolve_config.py` підтвердив українську мову та `docs/bmad` як output folder.
- `resolve_customization.py` підтвердив project overrides рев'ю, зокрема
  відсутність квоти зауважень. Прочитано фактичний каталог `bmad-help`.
- Skills у поточній розмові завантажуються з локальних файлів. Відображення
  нових команд у меню застосунку не перевірено; може знадобитися нова сесія.

Це перевірка встановлення та конфігурації, не тест майбутнього застосунку.

не застосовується до документації без коду. Окремо використано рубрику `bmad-prd`.
SC-14 і контроль рівного EPU додані за підсумками аудиту; межі повторної
перевірки цих змін зазначено у звіті. Початкові результати рев'ю не переписуємо.
