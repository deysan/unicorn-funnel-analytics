## Intent

Продовжити M1: підготувати бізнес-схему D1 та внутрішній шар збереження
ключів і результатів команд за погодженими D-031–D-037/D-065/D-083/D-090.
Зберегти відмінність між результатом, конфліктом, невідомим та простроченим
ключем; після семи діб не виконувати стару команду заново. Перевірити
повтори, конкурентні вставки й rollback на справжніх таблицях.
Без коміту/push, хмарних змін, застосування міграцій до dev, HTTP-маршрутів
або нових бізнес-рішень. Повний M1 та MVP цим підкроком не оголошувати готовими.

</frozen-after-approval>

## Implementation Notes

- Обмежений внутрішній блок сховища, без зовнішнього API. Невідомих
  продуктових рішень немає; усі міграції лише в ізольованих тестах.
  Наявні незакомічені зміни — попередній дозволений підкрок M1, зберігаємо.
- Нові файли: міграція бізнес-таблиць; `src/server/storage/command-results.ts`
  і `command-fingerprint.ts`; тести схеми, результатів та fingerprints;
  опис схеми. Використовуємо наявні D1 migrations/Vitest і guard.
- UTC-час у БД — INTEGER Unix milliseconds, ID — TEXT; каталог лишається
  конфігом. FK RESTRICT для профілю, доставки та причинних доказів.
  Історичні ClickID/EventID партнерських ключів/імітанта не FK: переживають
  джерело. Жодних cascade. Compact Lead не залежить від детальної події.
- Таблиці: users, clicks, events, partner_events, user_offer_leads,
  request_results, event_delivery, mock_received_events, capacity_control
  та окремий system_control. Ліміти/пауза/revision — наступні протоколи M1.
- Результати внутрішні й типізовані: accepted з EventID; offer_selected
  зі знімком переходу; no_offer з catalog_version. Сувора Zod-схема,
  4 KiB серіалізованого UTF-8, без сирих відповідей/email/payload.
- HMAC-SHA-256 окремим CryptoKey поза БД; формат 1 — рекурсивно сортований
  JSON перевіреного нормалізованого змісту + UserID/OperationID/тип.
  Нормалізація команд належить майбутньому командному шару, не цьому helper.
  Старий повтор використовує збережену версію ключа/формату; відсутність
  підтримки — технічна помилка, не конфлікт/нове виконання.
- Збереження повертає prepared INSERT для спільного batch; не виконує
  бізнес-команду або standalone commit. Читання та replay — read-only,
  після авторизації caller; cookie/контекст не імітуємо цими функціями.
- Given однаковий ключ/нормалізований зміст, when replay до 7 діб,
  then незмінний результат без повторного запису чи поновлення TTL.
- Given той самий ключ і змінений тип/зміст, when replay, then conflict;
  інший UserID із тим самим OperationID має окремий простір ключів.
- Given межа 7 діб або tombstone, when читання/replay, then expired
  незалежно від нового payload/доступності HMAC-ключа й затримки очищення.
- Given помилка або конкурентний INSERT у batch із бізнес-ефектами,
  when відмова, then жодних часткових записів; результат переможця можна
  прочитати й порівняти. Сам SQL-збій не означає успішного повтору.
- Given FK/retention, when очищення джерела, then залежності блокують
  передчасне видалення, а історичні ключі/Lead можуть пережити свої джерела.
- Незалежний агент звірив retention, HMAC, результат і FK з рішеннями.
  Перевірки: D1 schema/results, unit canonical HMAC, typecheck й загальний check;
  незалежне BMAD Build рев’ю без квоти findings перед завершенням.
