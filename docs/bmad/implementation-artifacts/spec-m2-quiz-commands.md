## Intent

Підключити до протоколу M1 перші три внутрішні команди квізу: вхід,
показ питання та підтвердження вподобання. Сервер читає профіль і компактні
Lead, визначає доступність кроку за правилами повернення й зберігає подію,
стан доставки, відповідь та результат команди атомарно. Читання контексту
повертає допустимі збережені відповіді, чинний email і підказку наступної дії.

Використати D-015, D-019, D-036–044, D-065, D-136, D-154–161,
D-167–168. Показ посилається на вхід, відповідь — на показ та через нього
на вхід; усі посилання належать цьому користувачу й преленду, мають
правильний тип/питання та логічний строк 90 діб. Після успішного запису
повтор повертає попередній результат без нової події й переоцінки кроку.
Інша відповідь під тим самим ключем — конфлікт. Нова відповідь змінює
лише своє поле; revision зростає тільки при фактичній зміні.

Given неповний профіль, when показ другого питання або email, then
відмова step_not_ready без ефектів. Given чинний Lead із правом bypass,
when новий показ/відповідь, then така сама відмова. Given конкурентна
зміна профілю, when revision конфліктує, then перечитування й максимум
три спроби зі старими ключами, payload та посиланнями. Given відсутній,
чужий або прострочений показ/вхід, when нова команда, then reference-відмова.
Given збережений прострочений email, when читання контексту, then email
не показується; саме читання не поновлює активність і не очищає дані.

Це внутрішній серверний підкрок M2. HTTP, cookie/bootstrap, UI, A/B,
постбеки та звіт лишаються наступними кроками. Без міграції робочої бази,
хмарних дій і коміту; незакомічений каталог попереднього підкроку зберегти.

## Implementation Notes

- Intent gaps: немає; джерело правил — погоджені рішення. Irreversibles:
  немає. Footprint: внутрішні quiz-модулі, читання профілю в storage,
  невелике розширення executor для перевіреної доменної відмови, D1-тести
  й документація. HTTP-контракт цим підкроком не оголошуємо реалізованим.
- Reuse: executeCommand, GuardedBatch, returningUserAction; без дублювання
  транзакційного протоколу. Профіль і Lead читати одним SQL-знімком;
  відмову за кроком також звіряти з revision, без резервування бюджетів.
- Технічні формати: question_id дорівнює полю профілю або email;
  preland_id — погоджений ASCII-формат. Експортний знімок schema_version=1
  містить ідентифікатори, тип, серверні timestamps та причинні посилання;
  значень відповідей/email у журналі немає.
- Перевірка: контрольований час, конкуренція й rollback на справжньому
  локальному D1; повний npm run check; окремий BMAD-review контекст.
- Реалізовано `storage/profile.ts`, `quiz/context.ts`, `quiz/commands.ts`;
  executor підтримує типізовану step-відмову з access/revision-guard
  і повторним читанням конкурентного результату, без бізнес-мутацій.
- Самоперевірка виявила особливість JS `$` перед кінцевим newline:
  нові DTO мають точну довжину UUID й абсолютний кінець preland regex;
  додано два регресійні випадки. Це виправлення формату, не нове рішення.
- Фактично пройшли 42 нові Worker-випадки. Фінальний
  `CI=true npm run check`: exit 0, 204 Vitest (81 unit + 123 Worker),
  типи/build і 21 Playwright. Браузерні тести стосуються каркаса M0.
- Незалежний BMAD Build review не виявив доказових дефектів; тести
  рев’юер читав, не запускав. Зауваження про uppercase UUID віднесене
  до майбутнього HTTP-адаптера D-077; внутрішній контракт канонічний.
  Коміт не виконували відповідно до доручення завершити цілий M2.
