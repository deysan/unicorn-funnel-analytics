## Intent

Після push і першої перевірки M0 почати M1 з найранішого технічного доказу
за implementation plan: перевірити SQL-guard D-162 у справжньому локальному
D1 runtime. Невдала передумова має відкотити всі записи batch; успішний
guard не залишає службових рядків. Підготувати першу службову міграцію
й перевірити її застосування в ізольованих тестових базах.
Без нової бізнес-поведінки, deploy, застосування до dev/demo-бази чи
коміту незавершеного M1. Повну бізнес-схему й командні протоколи додаємо далі.

</frozen-after-approval>

## Implementation Notes

- Джерела: D-065/D-162 та P-136, M1 у `docs/implementation-plan.md`.
  Невідомих продуктових рішень немає. Міграція в цьому підкроці виконується
  лише на синтетичних ізольованих тестових базах; незворотних змін немає.
  BMAD oneshot, коміт workflow відкладено до завершення всього M1.
- Файли: `migrations/0001_transaction_assertions.sql`,
  `vitest.worker.config.ts`, тестові типи й `tests/worker/transaction-guard.test.ts`.
  README, план, середовище та AI-worklog оновлюються за фактичними доказами.
- Службова таблиця має окремі іменовані CHECK для revision, доступу,
  посилань, місткості й кількості змін; NOT NULL закриває NULL-обхід.
  Неактуальні для конкретної перевірки колонки явно отримують 1 через default.
- Міграції читаються офіційним `readD1Migrations` у Node, застосовуються
  `applyD1Migrations` у workerd. SQL-фікстури `__guard_*` моделюють профіль,
  журнал, доставку, результат і бюджет; вони не є бізнес-схемою.
- Given успішна передумова, when batch завершується, then всі ефекти
  збережені й transaction_assertions порожня.
- Given стара revision, відсутній запис або NULL, when SQL обчислює guard,
  then batch відхилений і всі попередні/наступні ефекти відсутні.
- Given нуль змінених рядків, when перевірка changes() всередині batch,
  then вся транзакція відхилена, а не лише повернута помилка після commit.
- Given помилка наприкінці batch або конкурентний унікальний ключ,
  when виконання, then немає часткових ефектів чи залишків guard;
  конкурентний переможець має рівно один набір змін.
- Given файл міграції, when повторне apply, then міграція врахована один раз.
  Формат іменованих помилок перевіряємо на встановленому D1, без логування
  сирих помилок застосунком. Це не доказ повного командного retry/TTL-протоколу.
- Реалізовано 13 нових інтеграційних перевірок; `changes()` перевірено
  для 1 та 0. На поточному runtime CHECK-помилка містить власне ім’я
  constraint; NOT NULL/UNIQUE мають окремі повідомлення. Автоматичного
  класифікатора помилок чи command retry у застосунку ще немає.
- Фактичний `CI=true npm run check`: типи, 26 Vitest (6 unit + 20 Worker),
  build, 21 Playwright — успішні. Це локальна перевірка незакоміченого M1;
  GitHub run перевірив лише попередній коміт M0.
- Незалежне BMAD Build рев’ю: доказових дефектів у цьому підкроці немає;
  прочитано SQL, тести й документацію, перевірено diff. Рев’юер не
  запускав тести повторно. Findings/deferred work немає.
- Перевірено 75 локальних посилань. У 7 dev SQLite-файлах відсутні
  transaction_assertions та __guard_*; тестова міграція ізольована.
  Підкрок завершено без коміту; весь M1 ще триває.
